== Deployment View

Afunto runs in two shapes: the local developer stack, orchestrated by .NET Aspire from source, and the deployed runtime, where the same building blocks run as released container images.

This chapter describes both and which building blocks run where. How and where the deployed runtime is actually hosted, provisioned and operated is out of scope for this repository - this repository builds and publishes the images, and nothing more (see "Image Publishing" below).

=== Infrastructure Level 1

==== Local Development (.NET Aspire)

.Deployment View - Local Development
[plantuml, "deployment-local", png]
....
include::../images/deployment-local.puml[]

Motivation::
The entire stack runs locally via the .NET Aspire AppHost - see <<section-concepts>> under Development and Build for the one-command orchestration this relies on. Running everything from one command ensures environment parity across all contributor machines and eliminates manual setup of databases, Keycloak, or service dependencies.

Quality and Performance Characteristics::
Local development is optimized for fast iteration. All services run on `localhost` with no TLS. Keycloak runs the upstream image with a dev-file database and a relaxed, auto-imported realm; the backend and frontend run from source with hot reload.

==== Deployed Runtime

.Deployment View - Deployed Runtime
[plantuml, "deployment-server", png]
....
include::../images/deployment-server.puml[]
....

Motivation::
Away from a developer machine, the three building blocks this repository builds run as the release images described under "Image Publishing" below, against the same service types the local stack fakes: a PostgreSQL server, S3-compatible object storage, and an SMTP relay. Each image is configured entirely through environment variables at container start, so one build runs anywhere without a rebuild - the frontend image in particular resolves its API, Keycloak and storage origins at startup rather than at build time (see `frontend/AGENTS.md`).

Quality and Performance Characteristics::
Container images are the release artifacts, pulled by tag from GHCR. The backend applies EF Core migrations on startup when `Database:MigrateOnStartup` is enabled. The Application Database publishes no public route and is reachable only from within the runtime's own internal network; the Backend API is the only building block that talks to every other one, which is why an authentication gap there has the widest blast radius and why it validates every JWT against Keycloak's JWKS.

[plantuml, "deployment-cicd", png]

include::../images/deployment-cicd.puml[]
....

The CI/CD pipeline runs on GitHub Actions and covers three concerns: quality gates on every change, docs publishing, and release-time image publishing. This environment builds and verifies the building blocks rather than serving them, so there is no building-block-to-node mapping for it; the artifacts it produces are the images described above.

===== Quality Gate (on every push / PR to `main`)

The backend workflow (`dotnet.yml`) runs a `build` job (`dotnet restore` + `dotnet build` for the whole solution) that `format-check`, `fast-tests`, `integration-tests`, and `visual-tests` all depend on via `needs: build`, each downloading that build artifact instead of building its own copy:

* `format-check` - verifies `dotnet format`.
* `fast-tests` - `Application.UnitTests` and `ArchitectureTests`, no containers.
* `integration-tests` and `visual-tests` - both boot the Aspire AppHost stack (the same stack as local development) under Docker; `visual-tests` adds Playwright end-to-end checks.

The frontend workflow (`frontend.yml`) runs lint, i18n key-parity, type-check, and build; `lint.yml` enforces ASCII dashes and EditorConfig. `dotnet.yml`'s critical path is kept bounded and is actively tracked as the test suite grows - see TDR-2 for current timing data.

The architecture docs build (`docs.yml`) also builds on every pull request touching `docs/**`, as a build-only check - GitHub Pages publishing stays gated to pushes on `main`, so a docs PR can never publish a preview.

===== Image Publishing (on tag push)

Images are published to GitHub Container Registry (GHCR) on version tag pushes. A single Git tag releases all components at the same version:

.Published Images
[cols="1,2,2" options="header"]
|===
|Component |Tag format |Example

|Frontend
|`v{semver}`
|`v1.0.0`

|Backend
|`v{semver}`
|`v1.0.0`

|Keycloak
|`v{semver}`
|`v1.0.0`
|===

Release candidate tags (`v{semver}-rc.N`) publish images without moving the `latest` tag; stable tags (no `-rc` suffix) publish images and move `latest`. `publish.yml` stops there - what consumes a published tag, and where, is outside this repository. See link:https://github.com/maik-hasler/afunto/blob/main/VERSIONING.md[VERSIONING.md] for the full versioning and publishing strategy.
