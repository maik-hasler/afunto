=== Description

The backend CI workflow (`.github/workflows/dotnet.yml`) is the slowest quality gate on the project. It runs on every pull request and every push to `main` that touches `backend/**`, `frontend/**`, or `keycloak/**`, and it must pass before a change can be merged or released. The workflow builds the backend and then runs four test projects sequentially in a single job; the two that boot the full Aspire stack under Docker - `IntegrationTests` and especially `VisualTests` (TUnit.Playwright) - dominate its runtime.

The debt is not that the pipeline is unacceptably slow today, but that its runtime grows steadily and is concentrated in a single, ever-expanding job with no mechanism to keep it bounded. Left unmanaged, feedback latency keeps rising as the `VisualTests` suite grows.

=== Impact

==== Technical Impact

- *Developer feedback loop:* Every pull request and push waits ~10 minutes for the backend gate before it is known green; release candidates wait on `publish.yml` (~12 min) for the same suite. This is the single largest source of iteration latency.
- *Suite scalability:* All four test projects run sequentially in one job with no sharding or parallelism, so runtime grows linearly with every new `VisualTests` scenario - the suite cannot be extended without directly extending the critical path.
- *Maintainability:* Because `VisualTests` boots the full Aspire stack under Docker, a slow or flaky run is expensive to reproduce and diagnose, and any re-run costs the full ~10 minutes.

==== Business Impact

- *Cost control:* Longer runs consume more GitHub Actions minutes per pull request - relevant for a non-profit, volunteer-driven project with a minimal budget. Any parallelization that adds runners trades wall-clock time for total compute minutes.
- *Contributor experience:* Slow feedback raises the barrier to casual weekend contributions (persona Contributor Caro), working against the project's low-entry-barrier goal.

=== Symptoms

- *Dominant single step:* One step (`VisualTests`) consumes the majority of every backend CI run.
- *Rising duration over time:* Median run time roughly doubled over two months with no infrastructure change.
- *Full re-run cost:* A single flaky end-to-end assertion forces a complete ~10 minute re-run.
- *Stale documentation:* Earlier docs quoted a "20-30 minute" runtime that no longer reflected reality, a sign that pipeline cost was not being tracked.

=== Severity

High (raised from "Low to Medium" on 2026-08-20, see issue #2145).

The earlier rating rested on a ~10 min median that was "tolerable and well below the point of blocking work", with the debt framed as trajectory rather than present cost. The trajectory arrived: by 2026-08-20 the median was 21 min 58 s and only 36.4 % of runs completed at all. The thing that rose was not just runtime - `visual-tests` was failing 53 % of the time, which is the more important number, because a gate that is wrong every second run stops being a gate. The prediction in the original text ("severity rises toward High as the `VisualTests` suite expands") held exactly; the suite went from 117 tests at the time of #773 to 542.

Sharding (below) brings the wall-clock back under the original baseline. The severity stays High until the failure rate is measured back under 20 %, because runtime was only ever half of what made this debt expensive.

=== Proposed Solution

Ordered from cheapest quick win to larger strategic change. The project's Appropriateness and minimal-maintenance goals argue for stopping at the first options that keep runtime bounded.

Quick wins (low effort, low risk):

- *Keep the fast checks first:* `Application.UnitTests` and `ArchitectureTests` (~3 s each) already give near-instant feedback and run before the expensive Docker steps; keep that ordering so obvious failures fail fast.
- *Confirm caching is effective:* NuGet (`actions/cache`) and pnpm (`setup-node` cache) are already configured. Verify cache hit rates in the logs; the setup phase (~60 s) is already small, so there is little further to gain - do not over-invest here.
- *Skip Docker layer caching:* Image pull is only ~13 s (pre-pull step), so Docker layer caching is not worth the added workflow complexity at current numbers.

Structural (medium effort):

- *Split the two Aspire test projects into parallel jobs:* Run `IntegrationTests` and `VisualTests` as separate jobs so their wall-clock overlaps instead of summing. The critical path drops from ~10 min to roughly ~8 min (the longer job plus setup), at the cost of roughly doubled compute minutes and a duplicated build per job (mitigate by sharing the build output as an artifact).

*Eliminated the actual repeated-download source instead of centralizing the build (2026-07-28):*

- *Root-caused "gateway errors from downloading images repeatedly" against real CI logs* rather than assuming the three `docker pull` calls in "Pre-pull Docker images" were the cause - across several recent runs (both success and failure) that step consistently completed in ~10-15s with no errors. The actual repeated large download was `tests/VisualTests.csproj`'s `InstallPlaywrightBrowsers` MSBuild target (`AfterTargets="Build"`), which fetches Chrome for Testing + Chrome Headless Shell (~290 MiB combined) from `cdn.playwright.dev`. Because `integration-tests` and `visual-tests` both ran `dotnet build` against the whole `Afunto.slnx`, `integration-tests` was compiling (and therefore triggering the Playwright install for) `VisualTests.csproj` despite `IntegrationTests` never referencing it or using a browser - a pure wasted ~290 MiB download on every single run, on top of `visual-tests`' own (legitimate but also uncached) copy of the same download.
- *Fix:* scoped every test job's restore/build to just its own project (`dotnet restore tests/<Project>` / `dotnet build tests/<Project> --no-restore`) instead of the whole solution - `integration-tests` never touches `VisualTests.csproj` now, so it no longer pays that download at all. `visual-tests` additionally caches `~/.cache/ms-playwright` via `actions/cache` (keyed on `Directory.Packages.props`, matching the existing NuGet cache key convention), so the download that remains legitimate only happens once per Playwright version rather than on every run. Applied to both `dotnet.yml` and `publish.yml`.
- *Initially proposed scoping each job's build down instead of a single upstream `build` job whose artifact every test job downloads*, reasoning that `dotnet restore` is already cache-backed and cheap (the actual redundant network cost was the Playwright download above, not restore or the Docker pulls) and that a shared build crossing jobs via `actions/upload-artifact`/`download-artifact` would serialize setup+build (~2 min) *before* any test job starts, instead of today's model where each job's setup+build overlaps with the others in parallel - trading a faster critical path for fewer total compute-minutes, the wrong side of this project's stated trade-off (public-repo compute is free; wall-clock feedback latency is not - see the Business Impact section above).
- *Overridden on explicit request: adopted the single-`build`-job/artifact-fan-out shape anyway.* The repo owner weighed the wall-clock trade-off above and asked for it regardless - `dotnet.yml` now has one `build` job (`dotnet restore` + `dotnet build` for the whole `Afunto.slnx`) that `fast-tests`/`integration-tests`/`visual-tests` all depend on (`needs: build`) and consume via `actions/upload-artifact`/`download-artifact` (`publish.yml` mirrors this with `backend-build`). `format-check` stays independent (it never needed a build, only a restore, and is the one job that would lose the most by waiting). Two things confirmed empirically before shipping this, not assumed: (1) `dotnet run --project X --no-restore --no-build` still needs `~/.nuget/packages` physically present even with the artifact's `bin`/`obj` restored - without it, MSBuild project evaluation fails outright (`OutputType is 'Library'` instead of the test-SDK-contributed `Exe`) because it can't import the `.props`/`.targets` files packages contribute - so every downstream job still restores the same `actions/cache` NuGet key `build` populated, just never runs `dotnet restore` itself; (2) the artifact is genuinely large - the whole solution's `bin`/`obj` output measured ~567 MiB uncompressed / ~218 MiB zipped locally (each test project carries its own copy of shared framework dependencies like `TUnit`/`Aspire.Hosting.Testing`), so this trades some upload/download time on every run for one restore+build instead of three. Re-measure wall-clock once this has run for real; if the artifact-transfer cost turns out to dominate, sharding (below) is the next lever to reach for instead of reverting this. Two more things surfaced live, not in advance, both on the first real run of this shape: (3) `actions/upload-artifact`/`download-artifact` zip the artifact and don't preserve the Unix executable bit, so every downstream job's native apphost binary (`bin/.../<ProjectName>`, no file extension - what `dotnet run` launches directly) came back non-executable and failed `fast-tests`/`integration-tests` with "Permission denied"; (4) `upload-artifact` also excludes dot-prefixed files/folders by default, which silently dropped `tests/VisualTests`'s entire `bin/.../.playwright/` folder (the Playwright *driver* - a bundled Node.js runtime, distinct from the browser binaries in `~/.cache/ms-playwright`) from the artifact and failed `visual-tests` with "Driver not found", a different symptom from (3) since the file was missing outright rather than merely non-executable. Confirmed (4) by downloading the actual failed run's artifact and listing its contents rather than guessing. Fixed (3) with a `chmod +x` pass on every file under any `bin/` folder right after each `download-artifact` step (an initial version scoped to files with no extension in their name incorrectly skipped `Application.UnitTests`'s own apphost binary, since the *project* name itself contains a dot - dropped that filter entirely once discovered, since marking a `.dll`/`.json` executable is harmless), and (4) by setting `include-hidden-files: true` on the `upload-artifact` step.
- *`VisualTests` parallel-limit tightened for flakiness, not speed:* `VisualTestsParallelLimit` (`AssemblyParallelLimit.cs`) capped concurrent tests at `Environment.ProcessorCount`, which leaves zero spare CPU for the Aspire-hosted stack itself (backend/Postgres/Keycloak/frontend) once that many Chromium+axe-core tests are running - a plausible structural cause of the recurring "tips over the timeout" pattern already called out in `AuthHelper.GoToOrgAppDashboardAsync`'s comment (most recently: two `AccessibilityTests` methods timed out on the same `GET /v1/organizations` round trip in the same 2026-07-28 run). Changed to `Environment.ProcessorCount - 1` (minimum 1) to reserve one core for the stack. This is a structural mitigation, not a fix confirmed by controlled experiment - Docker/Aspire can't be run in a sandboxed session to load-test it locally, so treat it as a hypothesis to re-evaluate against real CI failure rates over the following runs; if flakiness persists, sharding (below) is the next lever, now for reliability as well as speed.
- *Found a second, distinct flake live on this change's own PR run:* `HomePage_HasNoSeriousA11yViolations` failed on a `color-contrast` violation against `text-brand-200` stats-row labels, which sit inside `global.css`'s `.animate-fade-up-d4` entrance animation (opacity 0 -> 1, staggered ~0.5s delay). Axe-core is deterministic given the DOM it's handed, so this was not the CPU-contention timing pattern above - it was a race between the scan and a still-fading element being caught at partial opacity, reading a lower (alpha-blended) contrast than the settled UI ever shows. Fixed at the source rather than in the one page it happened to surface on: `VisualTestBase` now overrides `ContextOptions` to set `ReducedMotion = ReducedMotion.Reduce`, which skips `global.css`'s `@media (prefers-reduced-motion: no-preference)`-gated animations entirely for every `VisualTests` browser context - the same rendering a real reduced-motion user gets, and immune to this race by construction rather than by timing the scan around it.

*What the measurements actually said* (56 `dotnet.yml` runs over 15.5 h, 2026-08-20):

[cols="3,1" options="header"]
|===
|Metric |Value

|`dotnet.yml` median wall-clock |21 min 58 s
|Completion rate |36.4 % (20 success / 20 cancelled / 15 failure)
|`visual-tests` median |19 min 25 s (~78 % of wall-clock)
|`visual-tests` failures |9 of 17 usable runs (53 %)
|`integration-tests` / `build` / `format-check` / `fast-tests` |4 min 19 s / 2 min 37 s / 2 min 26 s / 1 min 25 s, none notable
|===

This was never a "CI is slow" problem - 471 integration tests in 4 min 19 s is a good number. It was one job. The 20 cancelled runs are part of the finding rather than noise: `run_attempt > 1` was 0 across 210 runs despite 15 failures, so contributors were not re-running a red job, they were pushing over it and letting `cancel-in-progress` clean up. That is what a gate nobody trusts looks like.

*Root cause.* 542 tests on a 4-vCPU `ubuntu-latest` runner, with `AssemblyParallelLimit.cs` capping concurrency at `ProcessorCount - 2` (= 2), is ~271 sequential slots. 1165 s / 271 ~= 4.3 s per slot, which matches the measured median. The cap was not a mistake - it was tightened twice (`ProcessorCount` -> `-1` in the 2026-07-28 note above, then `-2`) precisely because CPU contention between Playwright/axe-core sessions and the Aspire stack they all call into was causing timeouts. But reducing parallelism buys reliability with runtime, and by 542 tests that trade had gone net-negative: it bought 19 minutes and roughly the same failure rate.

*Why B (sharding) and not A (a bigger runner).* A would have been a one-line change - `runs-on: ubuntu-latest-8-cores` and `ProcessorCount - 2` scales itself to 6 - and it addresses the measured cause head-on. It was rejected on cost, not on merit: only the default `ubuntu-latest`/`windows-latest`/`macos-latest` tier is free and unlimited on a public repository, and every larger-runner tier is billed per minute regardless of repository visibility (https://docs.github.com/en/billing/reference/actions-runner-pricing[GitHub Actions runner pricing]). That is incompatible with the minimal-budget constraint in this record's own Business Impact section. Sharding buys the same parallelism by adding runners rather than cores, and standard runners stay free, so it is $0 - the same reasoning #773 used.

*Measured fixed per-shard cost*, which is what decides how many shards are worth having (run 32337102365, `visual-tests`, 2026-08-20):

[cols="3,1" options="header"]
|===
|Segment |Duration

|Job setup (checkout -> Docker pre-pull complete) |1 min 43 s
|Aspire stack boot, inside the test step |~1 min (the first two tests were still flagged `[slow] still running after 1m 00s` with 0 completed)
|Test work |~15 min 50 s
|Test step total (TUnit self-reported 16 min 48 s) |16 min 50 s
|===

So roughly 2 min 45 s per shard is fixed and does not divide. At 4 shards that is ~3 min 50 s of test work each, for a ~6.5-7 min job and a ~9.5 min critical path once `build` (2 min 38 s) is added - under the 10 min target. Six shards would reach ~8 min end to end, and past that the fixed cost dominates entirely, so 4 is the point where the returns flatten rather than an arbitrary pick. The Aspire boot figure above had to be reconstructed from step timestamps and TUnit's `[slow]` lines; `AspireFixture` now times its own boot and both workflows print it (their "Report Aspire stack startup cost" steps), so the next revision of this table is a direct reading rather than an inference.

*How the shard split is expressed.* TUnit 1.65.31 has no native sharding flag - its documented flag set is `--list-tests`/`--treenode-filter`/`--maximum-parallel-tests`/etc., with nothing that splits a run across machines - so a shard is a Microsoft.Testing.Platform `--treenode-filter` over class names, which was #2145's stated fallback. The split is *computed* by `.github/scripts/visual-test-shard.sh` on every run rather than checked in: a hand-written list would silently stop running any newly added test class, since a class in no shard's filter is simply never selected. Classes are packed longest-first into whichever shard is lightest, because sizes are extremely uneven - `AccessibilityTests` alone is 90 of the 542 cases while most classes are 1-5 - which lands the four shards at 136/136/135/135 cases. The script fails loudly if a file's class name ever stops matching its file name, since that is the one way a class could fall out of every filter.

*`AssemblyParallelLimit` was deliberately left alone.* Each shard is still a 4-vCPU runner, so concurrency stays 2 and per-instant CPU contention per stack is unchanged - the win here is four stacks, not a busier one. Changing the parallel limit in the same commit would have confounded the one measurement this change exists to produce.

Strategic (larger change, defer until justified):

- *Move end-to-end tests off the per-PR critical path:* Keep build, unit, architecture, and integration tests on every pull request (fast and deterministic) and run the full `VisualTests` suite on a merge queue or nightly schedule instead of every push. This is the largest feedback-time win and best fits the Maintainability goal, at the cost of slightly later end-to-end signal.
- *Rebalance the test pyramid (issue #2148):* Move the bulk of the `VisualTests` suite down into `IntegrationTests` and `Application.UnitTests`, keeping end-to-end coverage only for what genuinely needs a browser. 542 end-to-end tests is roughly 24 % of the whole suite sitting in the slowest and most fragile layer, and sharding only divides that cost rather than removing it. The risk is deleting real coverage along with redundant coverage, which is why the guardrail below had to be recorded first.

*Why this and not line coverage.* Line coverage cannot answer the question #2148 raises. A redundant end-to-end test and a load-bearing one look identical to it: delete either, and the lines they touched are still executed by something else, so the percentage barely moves. *The concurrency trap - the most important finding here, because it decides whether the number is usable at all.* The first pass ran at Stryker's suggested `concurrency: 2` and produced 71.60 % / 73.47 %. *What could not move, and why the ~10 page-level smokes are the number they are.* Three classes of check are unavailable in jsdom, and they are not cosmetic:

- *Real focus and pointer behaviour.* The two skip links moving focus into `#main-content` (one per layout), the Leaflet marker's accessible name, and DOM order deciding which control a Tab reaches first.

So what stayed is one scan per distinct layout and palette - public landing, browse, opportunity detail, signed-in volunteer profile, my-signups, org app dashboard, engagement management, administration (4 sections), static legal page - plus the five browser-only assertions above. What left is every scan whose only difference from another was which component happened to be mounted: 68 methods, each of which booted the Aspire stack, signed a user in, seeded data and drove a browser to reach a dialog or a dropdown panel that renders from props.

*Residual coverage gap, stated rather than glossed.* Contrast inside states only reachable behind a modal or an edit-mode toggle - the org-settings edit form, the dashboard widget colour dialogs, the cancel dialogs - is no longer checked automatically; those states keep their structural and semantic coverage at component level and lose their contrast coverage. *Two costs that are not obvious until you run it, and one estimate that did not hold.* Every run pays a *3 min 21 s instrumented dry run* before a single mutant is tested, against ~50 s for the same suite uninstrumented - fixed overhead larger than the whole `checks / test` job (1 min 39 s). And the run is *slow in absolute terms*: 36 min 24 s for the cheap tier, against ~12 minutes for the backend's entire Domain + Application matrix. That gap is the whole reason the component tier stays on demand.

The estimate that did not hold is worth recording, because it was the basis for a configuration choice. Stryker warns that 111 static mutants (12 % of the 897) are estimated to take *69 %* of the run, and recommends `ignoreStatic`. Taking that recommendation: the flag excluded *57* mutants rather than 111, and the run still took 36 minutes. The pass without it was killed at 35 minutes before finishing, so the saving is real but its size is unmeasured - what is measured is that it does not make the run cheap. The flag stays (module-scope initialisation is excluded from the denominator as a result, which is the trade), but nobody should plan against that 69 % as recoverable headroom.

Three practical notes: under pnpm the plugin must be listed explicitly in `plugins` or Stryker reports no test runner found; `.stryker-tmp/` is a full copy of the project, so ESLint needs it in `ignores` or `pnpm lint` fails on its vendored coverage scripts after any local run; and the version is pinned for the same reason `dotnet-stryker` is - a new Stryker can add or drop mutators, and the score is only comparable across runs if the mutant set is.

*Shard count and `AssemblyParallelLimit`: still four and still `ProcessorCount - 2`, and the reason is a correction to this document's own framing.*

Measured on this branch's green run at 232 cases: `build` 2 min 12 s, shards *4 min 36 s / 5 min 21 s / 4 min 51 s / 5 min 04 s* (mean 4 min 58 s), `integration-tests` 4 min 23 s, *critical path 7 min 33 s* - against 9 min 05 s at 391 cases and ~9 min 50 s at 474. The model (`shard ~= 156 s + 2.1 s * (cases / N)`) predicts 4 min 38 s at N = 4 against an observed 4 min 58 s mean, so it still under-predicts the middle by ~20 s and tracks the tail; unchanged in character from the two runs above.

The fixed share is now *52 %* of a shard's wall clock (156 s of the 298 s mean), so the 50 % threshold recorded above has indeed been crossed. *It does not mean what this document said it meant.* A high fixed share means adding shards has stopped paying - not that removing them starts to. Folding a shard moves its cases onto the survivors, which are running in parallel, so as long as variable work is positive the critical path always gets worse:

=== Consequences of Delay

Deferring is acceptable in the short term - the pipeline is not yet a hard blocker. However:

- Runtime keeps climbing with each new end-to-end scenario, and the fix becomes more disruptive the larger the single job grows.
- Contributor feedback latency erodes the low-entry-barrier goal precisely as the project tries to attract more contributors.
- The gap between documented ("20-30 min") and actual (~10 min) runtime showed that pipeline cost was going untracked; without a tracked budget, regressions go unnoticed until they hurt.

=== Dependencies

- *Test isolation:* Sharding or parallelizing depends on `VisualTests` scenarios being independent and safe to run against separate Aspire stacks.
- *Budget:* Any option that adds runners or minutes depends on the project's tolerance for additional GitHub Actions cost.
